## Project

Agrotech platform for Nigerian smallholder farmers and agribusinesses: onboarding, KYC, farm/product management, embedded finance, and a B2B data marketplace. Vision is captured in two docs in this repo root:

- `agritech_revenue_model.html` — four revenue streams
- `agritech_microservices_architecture.html` — target polyglot microservices system

### Revenue model

- **Embedded financial services** (biggest earner, closes a $117B financing gap) — input financing on installment (12-30% interest margin), crop insurance commission (15-25%), farm-data credit scoring referred to MFBs for ₦3K-10K/loan referral fees.
- **B2B data & analytics** (70-85% margin, subscription) — aggregated field data sold tiered to agro-dealers (₦200K/yr), food processors (₦800K-2M/yr), gov/NGO food-security contracts (₦5M-50M).
- **Marketplace commission** (2-5% take rate) — direct farm-to-buyer trade with in-app escrow, cutting out the 30-50% middleman margins responsible for ~40% of Nigeria's harvest loss.
- **Freemium SaaS** (growth engine) — free weather/price/planting-calendar tier; premium (₦500-2K/mo: AI crop disease diagnosis, agronomic advice, loan access) targets ~15-20% conversion, ~₦1,200 ARPU.

### Target microservices architecture

Polyglot, gRPC inter-service, Kafka event bus, one DB per service, Docker/K8s on AWS Africa (Cape Town). Client layer: React Native mobile (SQLite offline) + API gateway (Kong/AWS).

| Service | Lang | Port | DB | Role |
|---|---|---|---|---|
| **Auth & user service** | Java/Spring Boot | 8080 | PostgreSQL | Identity, roles, farmer profiles, KYC — **this repo** |
| Fintech service | Java/Spring Boot | 8081 | PostgreSQL | Loans, insurance, credit scoring |
| Marketplace service | Go/Gin | 8082 | PostgreSQL+Redis | Listings, matching, transactions |
| Farm telemetry service | Go/Gin | 8083 | TimescaleDB | GPS/sensor/satellite ingestion |
| Notification service | Node.js | 8084 | Redis | SMS/push/WhatsApp, Kafka consumer |
| B2B analytics service | Node.js | 8085 | Read replicas+Redis | Dashboard API for B2B subscribers |
| AI/ML service | Python/FastAPI | 8086 | MongoDB | Crop disease, yield, credit-scoring AI |

**This repo (`An-Agrotech-application`) is the Auth & user service.** Per the architecture doc it owns identity, roles, farmer/business profiles, and KYC, and is a dependency of the Marketplace, Fintech, and Notification services. `server.port: 8080` in `application.yaml` matches the documented port exactly.

**2026-08-20 — scope decision from the user: everything in both HTML docs (all 7 domains — Auth, Fintech, Marketplace, Telemetry, Notification, Analytics, AI/ML) will be built in *this one* application, entirely in Java + Spring Boot.** The polyglot Go/Node/Python breakdown in the architecture table above is the original aspirational sketch and is superseded by this decision — treat the table as a feature/domain checklist, not a language plan. Future phases (Marketplace, Fintech, Telemetry, etc.) should be built as packages/modules within this same Spring Boot app, not separate services in other languages, unless the user says otherwise.

Still open: **Kafka vs RabbitMQ** — the architecture doc specifies Kafka as the inter-service event bus, but `application-local.yaml` in this repo is wired to RabbitMQ/CloudAMQP instead. Since everything is now one app, this may matter less (in-process calls instead of a message bus) — revisit when async workflows (loan events, notifications) are actually built.

### 2026-08-20 — Phase 1: real auth, built against a schema that was already there

Before writing any auth code, inspected the live local Postgres DB (`catalyst_users`) directly and found it already had tables no entity in the source tree mapped to: **`users`** (Spring-Security-`UserDetails`-shaped — `email`, `password`, `enabled`, `account_non_locked`, `role` with a check constraint `role IN ('FARMER','BUSINESS','ADMIN')`) linked from **`farmers.user_id`**, plus **`token_validation`** (OTP table — `verification_code`, `verification_type` smallint with a `0-2` check constraint that matches `auth.proto`'s `ValidateType{PHONE=0,EMAIL=1,LOGIN=2}` exactly) and extra `farmers` columns (`uuid`, `email_validated`, `phone_validated`) also unmapped. This is clearly the real intended auth schema from an earlier, fuller version of this app whose source was since lost — built new entities to match it exactly rather than inventing a new shape:

- `Entity/Users.java` + `Utils/Role.java` (`FARMER/BUSINESS/ADMIN`) + `Repositories/UsersRepository.java`.
- `Entity/TokenValidation.java` + `Utils/ValidateType.java` (`PHONE/EMAIL/LOGIN`, ordinal-mapped to match the smallint column) + `Repositories/TokenValidationRepository.java`.
- `FarmersDetails` — added `uuid`, `emailValidated`, `phoneValidated`, and a `user` (`OneToOne` via existing `user_id` FK) field.
- `OnboardingServiceImpl.createFarmer` now also creates the linked `Users` row (BCrypt-hashed password, `role=FARMER`) and sets `uuid`/`emailValidated`/`phoneValidated` — wrapped `@Transactional` since it's now a two-table write.
- `Security/JwtService.java` — HS256 JWT issuance/parsing via `jjwt` 0.12.6 (added to `pom.xml`; secret/expiry in `application-local.yaml` under `app.jwt.*`, same local-only-secret caveat as the DB password).
- `Config/SecurityConfig.java` — `BCryptPasswordEncoder` bean, and a permissive `SecurityFilterChain` (Spring Security was 401-ing every gRPC-over-servlet call by default with no filter chain defined at all). RPC-level authorization is deliberately **not** built yet — the plan is a gRPC `ServerInterceptor` reading the JWT from call metadata, not Spring Security's HTTP filter chain, since that's the correct model for gRPC; this is a documented gap, not an oversight.
- `AuthServiceImpl` — `farmerLogin` (verify hash, issue JWT), `validateEmail`/`validatePhone` (availability checks against `Users`), `generateToken`/`validateToken` (6-digit OTP issuance/redemption against `token_validation`, single-use, expiry-checked). `AuthController` now delegates to the service instead of falling through to the gRPC default `super.xxx()` (which was silently returning `UNIMPLEMENTED` for every RPC).
- **Not implemented, flagged honestly in code**: `changeFarmerPassword` — `ChangeFarmerPasswordRequest` in `auth.proto` carries only a `password` field with no email/userId/session-token to identify *whose* password to change. Needs a proto change (or the future JWT interceptor providing caller identity) before this can be built correctly.

Verified for real: `AuthTests.java` — signup→login round trip issues a real JWT, wrong password is rejected with `401`, `validateEmail` correctly flips from available→taken after signup, and the OTP generate/validate/reuse-rejected flow all pass against the live DB (`mvn test`: 6/6 passing, `OnboardingTests` + `AuthTests`).

### 2026-08-20 — Phase 3a: Fintech domain (loans, insurance, credit scoring) — first of the Phase 3 modules

Started Phase 3 with Fintech since the revenue model doc calls embedded financial services the biggest earner. Checked the live DB first, same discipline as Phase 2 — `\dt` showed no pre-existing loan/insurance/credit-score tables (unlike the Phase 1 auth-schema surprise), so this was a clean build with `ddl-auto: update` creating all 7 new tables directly, no manual `psql` DDL needed.

Built as a self-contained `fintech` proto package + Java package, replicating the `UsersService` vertical-slice pattern exactly (proto → entity with internal `id`/external `uuid` → repository → `@Service` impl returning `GrpcResponse<T>` → `@GrpcService` controller with the same `respond()` helper → `@SpringBootTest` against the real local DB with `@AfterEach` cleanup):

- **Proto** (`src/main/proto/fintech/`): `enum.proto`, `loan.proto`, `insurance.proto`, `creditscore.proto`, `service.proto` (`FintechService`, 13 RPCs). Enum value names are prefixed per-enum (`LOAN_APPLICATION_PENDING`, `POLICY_ACTIVE`, `CLAIM_FILED`, `REFERRAL_PENDING`, etc.) because protobuf top-level enum values share their package's naming scope — plain `PENDING`/`ACTIVE` reused across 5 status enums in one package would collide at compile time. Money/rate fields are `double` (matching the existing precedent in `products.proto`'s `price_per_unit`, not a new convention), converted to `BigDecimal` server-side.
- **Entities/Repos/Utils enums**: `LoanApplication`, `LoanAccount`, `LoanRepayment`, `InsurancePolicy`, `InsuranceClaim`, `CreditScoreRecord`, `MfbReferral`, each `@ManyToOne` to `FarmersDetails` via the existing `uuid` join convention. Java enum constant names deliberately match the proto enum names exactly (unlike `VerificationStatus`'s cleaner naming) specifically so the existing `Enum.valueOf(status.name())` mapping idiom keeps working without per-type switch statements.
- **`Services/Impl/FintechServiceImpl.java`**: business logic deliberately ties the three revenue-model features together instead of leaving them as unrelated CRUD stubs — `ComputeCreditScore` is a heuristic (not ML) score from 300–850 built from KYC-approval status, phone/email validation, having farms/products, and loan repayment history, banded POOR→EXCELLENT; `ApplyForLoan` derives its interest rate from the farmer's latest band (12% EXCELLENT → 30% POOR, defaulting to 25% with no score yet — matches the doc's 12–30% range); `ReferToMfb` requires an existing credit score (honest `412` error otherwise, same "don't fake it" convention as `getBusinessProfile`) and scales its referral fee ₦3,000→₦10,000 by band (matches the doc's ₦3K–10K range); `CreatePolicy` applies a fixed 20% platform commission (mid-range of the doc's 15–25%) to the premium.
- **`GrpcControllers/FintechController.java`**: wired all 13 RPCs.

Verified for real: `FintechTests.java` — one flow applies for a loan (confirms the no-score-yet 25% default rate), approves it, repays it to exactly zero balance across two repayments (confirms the `LOAN_COMPLETED` status flip and that both repayments come back on `GetLoan`); a second flow creates an insurance policy (confirms the 20% commission math), files and approves a claim; a third flow confirms `ReferToMfb` is rejected with `412` before any credit score exists, computes one (confirms the 300-point base score/`POOR` band for a brand-new farmer with no KYC/farms/loans), then confirms the referral succeeds with the `POOR`-band ₦3,000 fee. Full cleanup verified — row counts back to zero across all 7 new tables after the run. `mvn test`: 11/11 passing (8 existing + 3 new `FintechTests`, no regressions).

Not built in this pass (deliberately out of scope for the MVP slice, consistent with the "no gold-plating" project style): loan repayment schedules/amortization tables (single running `outstanding_balance` instead), a claims-payout disbursement step (claims stop at `CLAIM_APPROVED`/`CLAIM_REJECTED`, not `CLAIM_PAID`), and MFB referral acceptance/payment tracking (referrals stay `REFERRAL_PENDING`). No gRPC auth on these RPCs either — same pre-existing gap as every other service in this app, tracked under Phase 4 below.

### 2026-08-20 — Phase 3b: Marketplace domain (listings, orders, escrow, commission)

Second Phase 3 module, per the architecture table and the revenue model's "Marketplace commission (2–5% take rate) — direct farm-to-buyer trade with in-app escrow" line item. Live-DB check again showed no pre-existing marketplace tables — clean build via `ddl-auto: update`, same as Fintech.

**Existing-code finding surfaced during planning:** `FarmProducts` (built in Phase 2, the sellable item) has **no `uuid` field** — `FarmProductsRepository` has no `findByUuid`, and the existing `Products.id` proto field is populated from the raw numeric `product.getId()` (`OnboardingServiceImpl.java` `toProductProto`). This breaks the uuid-for-external-reference convention every other entity follows, but it's the already-shipped contract for `FarmProducts` — Marketplace listings reference products by that same numeric id (parsed from string) rather than silently changing `FarmProducts`' external identity. Worth fixing in a later pass if this actually becomes a public API surface, but out of scope here.

Built the same vertical slice as Fintech:

- **Proto** (`src/main/proto/marketplace/`): `enum.proto` (`ListingStatus`, `BuyerType`, `OrderStatus`, `EscrowStatus`, prefixed per-enum for the same collision reason as Fintech's), `listing.proto`, `order.proto`, `service.proto` (`MarketplaceService`, 11 RPCs).
- **Entities**: `MarketplaceListing` (`@ManyToOne FarmProducts` + `@ManyToOne FarmersDetails` as seller, denormalized the same way `Farms.farmers` is), `MarketplaceOrder` (`unitPrice`/`totalAmount`/`commissionAmount` snapshotted at order time so later listing price edits don't retroactively change existing orders; `buyerId` is a plain `String` — buyer is either a farmer or business `uuid`, deliberately not modeled as its own party entity).
- **`Services/Impl/MarketplaceServiceImpl.java`**: `CreateListing` checks the product actually belongs to a farm owned by the requesting farmer (`403` otherwise) — the one integrity check added beyond the plan's literal RPC list, since it's a one-line reuse of the existing `Farms.farmers`/`FarmProducts.farm` relations and prevents listing someone else's produce. `PlaceOrder` validates quantity against `quantityAvailable`, decrements it, flips the listing to `LISTING_SOLD_OUT` at zero, and applies a fixed 3.5% commission (mid-range of the doc's 2–5%) to the order total — same "platform sets its own commission" reasoning as Fintech's `CreatePolicy`. "Escrow" is bookkeeping state (`ESCROW_HELD/RELEASED/REFUNDED`) only — there's no real payment gateway in this codebase, so no actual funds movement happens; `ConfirmOrder`(reject)/`CancelOrder` both restore the listing's `quantityAvailable`.
- **`GrpcControllers/MarketplaceController.java`**: wired all 11 RPCs.

Verified for real: `MarketplaceTests.java` — one flow creates a farmer/farm/product (reusing `OnboardingService`, no duplicated setup logic), lists it, places an order (confirms the 3.5% commission math and the listing's remaining quantity), accepts and completes it (confirms `ORDER_COMPLETED`/`ESCROW_RELEASED`); a second flow places then cancels an order and confirms the listing's `quantityAvailable` and `LISTING_ACTIVE` status are fully restored. Full cleanup verified — row counts back to zero across both new tables. `mvn test`: 13/13 passing (11 existing + 2 new `MarketplaceTests`, no regressions).

Not built in this pass, same "MVP slice, no gold-plating" boundary as Fintech: no real payment/escrow integration (bookkeeping only, as above), no listing edit/delete RPCs (only create + read), no partial-quantity delivery tracking on `CompleteOrder`. No gRPC auth here either — same pre-existing gap, Phase 4 item.

### 2026-08-20 — Phase 3d: Notification domain (SMS/push/WhatsApp)

Fourth Phase 3 module, per the architecture table's "Notification service — SMS/push/WhatsApp, Kafka consumer." Live-DB check again showed a clean slate.

**Existing-code finding:** `FarmersDetails` already has unused `smsEnabled`/`emailEnabled` columns from the Phase 0 skeleton (populated at signup, never read by any RPC). These cover a different channel set (SMS/email, not the doc's SMS/push/WhatsApp) and only apply to farmers, not business/admin recipients — so a dedicated, recipient-type-agnostic `NotificationPreference` entity was built instead of reusing or duplicating those two fields. Deliberate, not missed.

**Accepted simplifications, same category as the open Kafka-vs-RabbitMQ and TimescaleDB notes:** the doc specifies Redis (this app has one shared Postgres DB, so notifications are a plain table) and a Kafka consumer (other domains would publish notification events; since everything's in-process now, nothing auto-publishes here yet — `SendNotification` is a direct call other domains' service code could make in-process later). There is also no real SMS/push/WhatsApp gateway anywhere in this codebase (no Twilio/FCM/WhatsApp Business API client) — `SendNotification` simulates dispatch (logs it, marks `SENT`) rather than faking a real delivery, same "bookkeeping, not the real thing" boundary as Fintech's claims-payout and Marketplace's escrow.

- **Proto** (`src/main/proto/notification/`): `enum.proto` (`RecipientType` matching `Role`'s three values, `NotificationChannel` matching the doc's SMS/push/WhatsApp exactly, `NotificationStatus`, prefixed per-enum for the usual collision reason), `notification.proto`, `preference.proto`, `service.proto` (`NotificationService`, 7 RPCs). The `Notification` message collides with its file name the same way `Kyc`/`kyc.proto` did in Phase 2 — generates `NotificationOuterClass`, same resolution.
- **Entities**: `Notification` (`recipientId` is a plain `String`, no FK — same no-enforcement pattern as Marketplace's `buyerId`, since a recipient can be a farmer, business, or admin), `NotificationPreference` (one row per recipient, `smsEnabled`/`pushEnabled`/`whatsappEnabled`, absence treated as all-enabled defaults rather than requiring every recipient to explicitly opt in).
- **`Services/Impl/NotificationServiceImpl.java`**: the one real piece of logic — `SendNotification` checks the recipient's preference for the requested channel before "sending"; if disabled, the notification is saved as `NOTIFICATION_FAILED` with an honest reason instead of silently dropping it or pretending it went out. This is the same "gate the action on a real signal" shape as Fintech's credit-score-gates-referral. `GetNotificationPreferences` returns synthesized all-true defaults (not persisted) when a recipient has never set preferences, so a recipient who's never touched settings is still reachable rather than erroring.

### 2026-08-20 — Phase 4a: Flyway migrations (replaced `ddl-auto: update`)

Converted the schema — 28 tables, all built via `ddl-auto: update` since Phase 0 — into a versioned Flyway baseline rather than continuing to let Hibernate silently auto-DDL it, per the gap flagged since Phase 2.

**Not a redesign — a lock-in of current reality:** `pg_dump --schema-only` (v16 client, matching the local server; had to `brew install postgresql@16` since only a v14 client was present and pg_dump refuses cross-major-version dumps) captured the exact DDL Hibernate had already generated, cleaned of session/meta noise (`\restrict`/`\unrestrict` psql markers, `SET` statements, `SELECT pg_catalog.set_config`; `OWNER TO`/`GRANT`/`COMMENT ON` were never present thanks to `pg_dump --no-owner --no-privileges --no-comments`), into `src/main/resources/db/migration/V1__baseline.sql`. No column, type, or constraint was changed.

**Real discovery, not a configuration mistake:** the first pass (`flyway-core` + `flyway-database-postgresql` deps, `spring.flyway.*` config) compiled and all tests passed, but silently did nothing — no `flyway_schema_history` table, no Flyway log lines at all. Root cause, found via the Spring condition-evaluation report and inspecting the actual jars on this project's classpath: **Spring Boot 4.0.5 (the version this project is pinned to) moved Flyway autoconfiguration out of `spring-boot-autoconfigure` entirely**, into a new dedicated `org.springframework.boot:spring-boot-flyway` module (`org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration` — note the package moved too, out from under `org.springframework.boot.autoconfigure.flyway`) — part of the same aggressive per-feature modularization visible elsewhere in this Boot version's dependency tree (`spring-boot-jdbc`, `spring-boot-hibernate`, `spring-boot-persistence`, etc., versus the monolithic `spring-boot-autoconfigure` older Boot versions used). Adding `spring-boot-flyway` explicitly to `pom.xml` fixed it. Worth remembering for any future Spring Boot 4.x dependency that "used to just work from spring-boot-autoconfigure" — check whether it moved to its own module first, don't assume silent non-activation means misconfigured YAML.

- `pom.xml` — added `spring-boot-flyway`, `flyway-core`, `flyway-database-postgresql` (all version-managed by the `spring-boot-starter-parent` BOM).

### 2026-08-20 — Phase 4c: gRPC JWT interceptor (RPC-level auth) — Phase 4 complete

Closed the gap `SecurityConfig.java`'s comment has flagged since Phase 1: gRPC calls ride over Tomcat via `spring-grpc-server-web`, so Spring Security's HTTP filter chain is the wrong layer for RPC auth — a gRPC `ServerInterceptor` reading the JWT from call metadata is the correct mechanism, and this builds it.

**Scope boundary, stated up front (matches this codebase's established honesty convention):** this is **authentication** only — reject calls with no/invalid JWT, and expose the caller's parsed claims to service code via a gRPC `Context` key. It does **not** add per-resource **authorization** (e.g. verifying a farm being modified actually belongs to the caller) — that would mean touching every one of the 68 RPC handlers individually and is a materially larger, separate effort.

- `Security/JwtAuthServerInterceptor.java` (`@Component @GlobalServerInterceptor implements ServerInterceptor`): registration uses `org.springframework.grpc.server.GlobalServerInterceptor`, a marker annotation `spring-grpc-core` ships specifically for wiring a `ServerInterceptor` bean into every registered `@GrpcService` automatically — exactly the extension point the Phase 1 comment described, no per-controller wiring needed. Reuses `JwtService.parseClaims` (already existed, no new JWT logic) rather than reinventing token parsing.

Everything else — all remaining RPCs across all 8 services — now requires a valid `authorization: Bearer <jwt>` header. `ChangeFarmerPassword` deliberately stays **off** the allowlist even though it's still a `501` stub (from Phase 1) — requiring a token here is exactly the caller-identity mechanism that stub has been waiting on.

So today's token doesn't let a caller's identity be matched against farm/business ownership without an extra repository lookup — exactly the authorization work this pass explicitly excluded. Left as a note for whoever builds that next, not silently worked around.

### 2026-08-20 — Real bug found and fixed: `JwtAuthServerInterceptor` broke for direct (non-gateway) gRPC clients

User asked for a sample `grpcurl` command to see the auth-failure error, then asked to actually run it. Running it directly against the backend (bypassing the Envoy gateway entirely — `grpcurl -plaintext localhost:8080 telemetry.TelemetryService/GetFarmTelemetrySummary`, no token) did **not** return the expected `UNAUTHENTICATED` — it returned `Internal: server closed the stream without sending trailers` (and on a retry, `RST_STREAM ... INTERNAL_ERROR`). Every prior verification of this interceptor (`JwtAuthServerInterceptorTests`'s Mockito unit tests, and the live gateway smoke tests) had exercised it either through mocks or through Envoy — **this was the first time anyone had pointed a raw, direct gRPC client at a protected RPC**, and it surfaced a real defect that had been there since the interceptor was built.

**Root cause, isolated methodically, not guessed:** confirmed `grpcurl -plaintext ... list` (reflection, unauthenticated-allowlisted) worked fine — so basic HTTP/2 cleartext connectivity to Tomcat was never the problem. Confirmed a normal *successful* protected-adjacent call (`ValidateEmail`, which returns via ordinary `onNext`/`onCompleted`, never touches `call.close()` directly) also worked fine over the same raw path. That isolated the fault to exactly one thing: `JwtAuthServerInterceptor`'s early-rejection pattern — `call.close(status, trailers)` invoked directly from the interceptor, before `next.startCall()`/`Contexts.interceptCall()` ever runs. That's the textbook, officially-documented grpc-java interceptor pattern for rejecting a call before it reaches business logic, and it works correctly on Netty-based gRPC transports — but this app serves gRPC over Tomcat via `grpc-servlet-jakarta` (confirmed on the classpath), and that specific transport does not correctly emit a trailers-only HTTP/2 response when `close()` is called without `sendHeaders()` ever having run first. A gRPC-Web client going through Envoy apparently tolerated or normalized the malformed response (which is exactly why every prior test — including last session's explicit "confirm auth enforcement survives gRPC-Web translation" check — looked clean); a direct native gRPC client did not.

**Fix**: `JwtAuthServerInterceptor`'s two rejection branches now call `call.sendHeaders(new Metadata())` before `call.close(...)` — a one-line addition per branch, factored into a shared `rejectUnauthenticated` helper, with the reasoning commented inline so it doesn't read as a stray/superfluous call to whoever touches this next. This is a workaround for the servlet-transport's limitation, not a correction to the interceptor's logic — worth remembering if this app ever moves off `grpc-servlet-jakarta` onto a Netty-based gRPC server, at which point the workaround becomes unnecessary (but harmless to leave).

Verified for real: rebuilt, ran a fresh backend instance with visible logs (the first repro was against a separately-running instance started via IntelliJ outside this session's control, so its logs weren't accessible — started a second instance specifically to get full log visibility for root-causing this), reproduced the bug, applied the fix, and confirmed both rejection branches now return correctly (`Unauthenticated: Missing bearer token` for no token, `Unauthenticated: Invalid or expired token` for a garbage token) via direct `grpcurl` — no gateway involved. Confirmed normal successful calls are unaffected. Full suite re-run: `mvn test` 25/25, no regressions.

This is exactly the kind of gap that "verified through the gateway" can hide — worth remembering for future auth/interceptor work: test the direct path too, not just the path the mobile app will actually use.

### 2026-08-20 — Same bug, much bigger scope: generalized the fix to every business-level error, not just auth rejections

User asked to fix the same `sendHeaders`-before-`close` issue for "successful early-close cases too" — i.e., the ordinary business-level error responses every controller returns (404 `NOT_FOUND`, 409 `FAILED_PRECONDITION`, 403 `PERMISSION_DENIED`, etc.), not just `JwtAuthServerInterceptor`'s auth rejections. Checked before assuming: every one of the 8 controllers' `respond()` helpers calls `responseObserver.onError(statusException)` for these — and `StreamObserver.onError()` is itself implemented via a bare `ServerCall.close()` with no prior `sendHeaders()`, the exact same shape as the auth-interceptor bug just fixed. Reproduced live: `grpcurl` against `fintech.FintechService/GetLoan` with a valid token but a nonexistent `loan_id` returned the same `Internal: server closed the stream without sending trailers` instead of `NotFound`. **This means every non-2xx business response across all 68 RPCs was broken for direct gRPC clients**, not just the auth path — a much bigger deal than the previous fix alone addressed.

**Fixed once, generally, instead of patching all 8 controllers:** `Security/HeaderSafeServerCall.java` — a `ForwardingServerCall` wrapper that tracks whether `sendHeaders()` has run yet, and if `close()` is called first, sends empty headers automatically before delegating — safe and idempotent (only ever sends headers once, whichever caller does it first). `JwtAuthServerInterceptor` (the one global interceptor already covering all 8 services) now wraps every `ServerCall` in this at the top of `interceptCall`, before the public/protected branch — so it applies to every RPC in the app, success or error, auth-related or not, without touching any controller. The manual `sendHeaders()` call added to the previous fix's two rejection branches is now redundant and was removed — the wrapper handles it generically.

Verified for real: rebuilt, restarted the debug instance, and confirmed all three paths through the same wrapper — a genuine business 404 (`GetLoan` on a nonexistent id) now correctly returns `NotFound: Loan account not found`; the auth rejection path still correctly returns `Unauthenticated`; a normal successful call is unaffected — all via direct `grpcurl`, no gateway. Added `HeaderSafeServerCallTests.java` (in the same package, since the class is intentionally package-private) testing the wrapper directly: `close()` without a prior `sendHeaders()` sends empty headers first, in order, before closing; `close()` after headers were already sent by the normal success path does **not** send them a second time (which would itself throw — gRPC transports reject a duplicate `sendHeaders()` call). Two of the four existing `JwtAuthServerInterceptorTests` needed a small update (`eq(call)` → `any()` for the `startCall` argument, since the interceptor now legitimately passes a wrapped call object, not the original mock — the test was asserting incidental object identity, not anything about actual behavior). Full suite: `mvn test` 27/27 (25 previous + 2 new), no regressions.
